1. Tests + CI

Esfuerzo: 5–7 días · Tier: 1 (hacer ya) · ROI: Alto

Estado actual

  • Sin runner de tests, sin tests existentes.
  • CI = solo deploy.yml (SSH + docker compose).
  • TypeScript ya brinda garantías de tipos.

Stack propuesto

  • Vitest — mejor integración Next.js que Jest, ESM nativo, ~10x más rápido.
  • @testing-library/react + jest-dom para componentes.
  • Playwright para E2E (un solo flujo crítico, no full coverage).
  • MSW (Mock Service Worker) para interceptar fetch en tests.

Estructura

__tests__/
  unit/           ← lib/, services/ puros
    pricingUnits.test.ts
    fx.test.ts
    carbonService.test.ts
    tierLogic.test.ts
  integration/    ← API routes con DB en memoria/mock
    api-mcp.test.ts
    api-fx.test.ts
  components/     ← React Testing Library
    PinButton.test.tsx
    CurrencySelector.test.tsx
  e2e/            ← Playwright
    login-flow.spec.ts
    onboarding.spec.ts

Cobertura objetivo (MVP)

  • 80% lib/: helpers puros, fáciles y críticos (pricingUnits, fx, carbon, tierLogic, requestAuth).
  • 60% services/: mock de pool DB, validar lógica.
  • 40% API routes: smoke tests de respuestas + auth.
  • 3 flujos E2E: login → dashboard, crear budget, ver costos.

CI workflow nuevo .github/workflows/ci.yml

on: [pull_request, push]
jobs:
  lint:       npm run lint
  typecheck:  npx tsc --noEmit
  unit:       npm test -- --coverage
  e2e:        npx playwright test  (matrix node 20)
  build:      npm run build  (verifica que compila)

2. SSO SAML

Esfuerzo: 3–5 días (homebrew) · 1–2 días (WorkOS) · Tier: 1 · ROI: Alto Enterprise

Estado actual

  • Auth solo Entra ID (OAuth/MSAL).
  • Tabla Users con entra_oid + email.

Por qué SAML

Clientes Enterprise grandes usan Okta, Auth0, OneLogin, Ping, Google Workspace SAML. Sin SAML, cierran negocios alternativos. Es el dealbreaker más citado en RFPs.

Stack

  • @node-saml/passport-saml (mantenido, soporta Next.js).
  • O WorkOS / Auth0 Enterprise Connections (managed, ~$0.05/user). Recomendado para MVP por time-to-market.
  • Almacenamiento: nueva tabla TenantSAMLConfig.

Schema

CREATE TABLE TenantSAMLConfig (
  tenant_id VARCHAR(128) PRIMARY KEY,
  entity_id VARCHAR(255),
  sso_url VARCHAR(512),
  certificate TEXT,
  attribute_mapping_json JSON,
  enabled BOOLEAN DEFAULT 0,
  enforced BOOLEAN DEFAULT 0,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

Endpoints nuevos

  • GET /api/auth/saml/[tenantId]/login — redirige al IdP.
  • POST /api/auth/saml/[tenantId]/acs — Assertion Consumer Service.
  • GET /api/auth/saml/[tenantId]/metadata — XML para configurar IdP.
  • /api/admin/sso — UI config (upload cert, set URL, attribute mapping).

Flujo

  1. Tenant admin va a /admin/sso, configura IdP (URL + cert).
  2. Genera URL /api/auth/saml/<tenant>/login y la comparte con su IdP.
  3. Usuario → "Login with SSO" → ingresa email → detectamos dominio → redirige al IdP → callback al ACS → emitimos nuestro JWT.
  4. Si enforced=true, usuarios del dominio NO pueden hacer login via Entra/local — solo SAML.

Sprints

DíaEntregable
1Schema + endpoint metadata + UI básica
2Login init + ACS callback con @node-saml
3Attribute mapping (email, name, role) + crear/sincronizar User
4UI admin SSO + tests con SAMLtest.id (idp gratuito de prueba)
5Doc onboarding para Okta/Auth0/Google Workspace + edge cases (logout SLO)

Alternativa rápida — WorkOS (1-2 días total)

  • Una sola API key, ellos manejan los IdPs.
  • $0.05/user/mes (negociable a fixed pricing >100 users).
  • Entregás SAML + SCIM provisioning + Directory Sync de paso.
  • Recomendado si el time-to-market importa más que el costo.

5. Anexo — Integración AWS (estado y esfuerzo)

Lo que ya está (5%)

  • providerFactory.ts con stub para AWS (comentado).
  • awsFocusMapper.ts (56 LOC) — mapper CUR → FOCUS, esqueleto.
  • Interfaz CloudProvider abstrayendo Azure (preparada para multi-cloud).

Lo que falta

  • SDK AWS (@aws-sdk/client-*).
  • AWSProvider real (auth via IAM Role + AssumeRole cross-account).
  • CUR (Cost and Usage Report) ingestion desde S3.
  • Equivalentes: ResourceGraph (→ Tag Editor / Resource Explorer), Advisor, Reservations Recommender, Trusted Advisor, Carbon footprint, Compute Optimizer.
  • DB schema multi-cloud (hoy todo es subscription_id; AWS necesita account_id + region).
  • Onboarding UI para AWS (Connect to AWS → bootstrap CloudFormation template).
  • Pricing API AWS (Azure Retail Prices ≠ AWS Pricing API).
