## Detalle por tema

### 0. Power Schedules — bug "apagado/reinicio no ejecuta" (RESUELTO, pendiente de deploy)
Usuario reportó: encendido funciona, apagado y reinicio no. Investigación:
- Se descartó asimetría en `remediationService.ts` (las 3 funciones start/
  deallocate/restart son simétricas) y en el rol RBAC de onboarding
  (`src/lib/onboardingScriptTemplate.ts` sí incluye las 3 `Microsoft.Compute/
  virtualMachines/{start,deallocate,restart}/action` — el generador viejo
  `scripts/onboarding_module.py` que le faltaba `restart` es legacy, no se usa).
- Por SSH al VPS se confirmó que producción está en `5ad6237`, **anterior**
  a los fixes `945b2d3`/`0dd5320` — es decir, prod corre la versión con el
  bug real en `executeDueSchedules`: `setHours` usaba el reloj local del
  proceso Node en vez de operar sobre el epoch ya desplazado por
  `gmt_offset`, y `String(date)` de una columna `Date` de mysql2 no da
  formato ISO (rompía la comparación "ya se ejecutó hoy"). Con timezone del
  proceso ≠ GMT-3 (o cualquier corrimiento de reloj), el matching de
  fecha/hora fallaba silenciosamente para acciones que no fueran la primera
  evaluada.
- **Reproducido y verificado en local** (DB local + `npm run cron:power-schedules`)
  contra Azure real (VM `processinspector`, RG `rpa365-inspector`), con el
  código YA corregido (post `0dd5320`):
  - `STOP_VM` → `ActionLogs` id 41, `SUCCESS` (17:51:24)
  - `START_VM` → `ActionLogs` id 42/40, `SUCCESS`
  - `RESTART_VM` → `ActionLogs` id 43, `SUCCESS` (17:59:48)
  - Los 3 tipos de acción ejecutan correctamente end-to-end (DB → cron →
    Azure SDK → `ActionLogs`) con el código local actual.
- **Conclusión**: no hay bug de código nuevo — es el mismo bug que ya se
  había corregido en `945b2d3`/`0dd5320`, simplemente **no desplegado**.
  Una vez autorizado el push + deploy a `main`, el problema debería
  desaparecer en producción sin cambios adicionales.
- Nota operativa: en dev local no hay cron periódico real corriendo (solo
  `npm run cron:power-schedules` manual) — si un schedule "no se ejecuta" en
  local puede ser simplemente que nadie disparó el cron, no un bug.

### 1b. Copilot FinOps — "El asistente no pudo generar una respuesta"
Bug reportado en prod tras el cambio de modelo a `claude-sonnet-5`: el chat
del Copilot (widget flotante, `GlobalCopilot.tsx`) devolvía el mensaje
genérico de error aunque la config de IA (global y por-tenant) estaba bien.
Logs del VPS confirmaron la causa: `AI_APICallError: "temperature is
deprecated for this model"` — Claude Sonnet 5 (y Opus 4.7+) rechazan con 400
cualquier `temperature` no-default; `claude-3-opus-20240229` (el modelo viejo)
sí lo aceptaba, por eso el bug apareció recién con el cambio de modelo. El 400
llega después de que el stream ya arrancó, así que el cliente solo ve el
stream cortarse sin contenido — de ahí el mensaje genérico.
- Archivo: [`src/app/api/intelligence/copilot/route.ts`](src/app/api/intelligence/copilot/route.ts) —
  se quitó `temperature: 0.2` del `streamText()` (único uso de `temperature`
  en todo el código). El endpoint es provider-agnóstico (google/openai/
  deepseek/azure/anthropic según config del tenant), así que no hay un valor
  universal seguro — sin el parámetro, cada proveedor usa su default.
- Verificado con logs del VPS antes y después del deploy (`docker logs
  finops-finops-app-1 --since Xm | grep -i 'Copilot\|temperature'`).
