## 1. Bugs reales encontrados y arreglados en Invoicing Report

Todo reportado en vivo por el usuario probando contra el tenant real
RPA365 SA (`54d7cf18-0baa-4da7-8242-fbf59a92aaac`).

### Email (`src/app/api/admin/report/invoicing/email/route.ts`)
Reescrito completo — nunca se había actualizado cuando se arregló la ruta
principal:
- Columnas inexistentes: `partner_markup_percent` → `markup_percentage`;
  `cs.billed_cost` → `COALESCE(EffectiveCost, BilledCost, cost_usd, 0)`.
- Solo aceptaba período `YYYY-MM` exacto; con `last3m` (default de la UI)
  siempre devolvía "No data found". Se extrajo `resolvePeriodRange` a
  `src/lib/invoicingPeriod.ts` (única fuente de verdad, usada por ambas
  rutas) para que esto no vuelva a divergir.
- Gate de tier era Enterprise, la ruta principal ya era Business+ —
  desalineado, corregido a Business.

### PDF (`src/lib/pdf/showbackInvoice.tsx`)
`renderShowbackPdf` crasheaba con `<Document>` de 0 páginas cuando un
cliente no tenía líneas en el período — rompía el ZIP completo ("Download
All") si UN SOLO cliente estaba vacío. Fix: `Math.max(1, ...)` páginas.

### PBIT — de stub a exportable de verdad
No se intentó armar el binario `.pbit` a mano (ZIP con partes internas de
Power BI Desktop — modelo, layout — muy fácil de dejar corrupto). En su
lugar:
- `src/app/api/exports/powerbi-feed/route.ts` (infraestructura MCP API Key
  ya existente) ganó `type=invoicing&period=...` — feed tenant-scoped
  autenticado por API Key (no JWT MSAL, que Power BI Desktop no puede
  refrescar).
- El GET principal, con `format=pbit`, genera un `.pbids` (Power BI Data
  Source, formato JSON documentado por Microsoft) apuntando a ese feed.
  Power BI Desktop lo abre y pide la API Key una vez (se genera en
  Configuración → API Keys, mismo tier Business).

### Selector de mes libre
`InvoicingReportPanel.tsx` solo ofrecía "Últimos 3 meses" + 3 meses fijos
en un `<select>`. Se agregó un `<input type="month">` en paralelo,
acotado a la ventana de retención real de Azure (13 meses).

### Bug bonus encontrado de paso: CSV/JSON 401 silencioso
`handleDownloadCsv`/`handleDownloadJson` usaban `window.open()`, que no
puede mandar el header `Authorization` — en cualquier tenant real (no
mock) esas descargas devolvían 401 sin mostrar error. Cambiado a
`fetch`+blob, mismo patrón que ya usaba el PDF.

### Drift de redondeo en el markup
Redondear el `adjustedCost` **por línea** y sumar esos redondeos ya
redondeados acumulaba drift — con markup 0% se veía "Monto Markup:
-$0.06" en vez de $0. Fix en `route.ts` y `email/route.ts`: agregar sin
redondear, redondear una sola vez al final sobre cada total (`totals`,
`byCustomer`, `byInvoiceSection`, `bySubscription`).

### Cliente/Customer ID en blanco
`customer_id` puede venir `NULL` en billing EA/MCA sin cliente CSP
asociado (vs. tenants revendidos vía partner, que sí lo tienen). Antes se
mostraba vacío. Se introdujo un sentinel corto (`NO_CUSTOMER_ID =
"unassigned"`) como `customerId` real + un campo `customerName` separado
("Sin identificar...") solo para mostrar — **importante**: el primer
intento de fix usaba directamente el label largo como `customerId`, lo
cual rompía el filtro de PDF/email al viajar por URL. Corregido al
sentinel corto antes de deployar.

### `customerId=null` literal en PDF/Email (401/404 reportados por el usuario)
Root cause: el navegador tenía cacheado (SWR, en memoria) un `byCustomer`
de ANTES del fix anterior, donde `customerId` todavía podía ser `null`
real de JS — el botón mandaba `&customerId=null` literal. Se agregaron
guards en 3 capas: cliente (no dispara la request si `customerId` es
falsy, pide recargar), y ambas rutas server (rechazan explícitamente el
string `"null"`/`"undefined"` con mensaje claro en vez de 404/400 genérico).

## 3. Mejoras estructurales (pedidas explícitamente tras el incidente)

### a) Guard anti-vaciado ahora por-suscripción
`scripts/recalculate-cost-snapshots-usd.ts`: `deleteTable()` acepta un
filtro opcional `subscriptionIds`; `maybeReplace()` solo borra/reemplaza
las suscripciones que trajeron datos frescos en la corrida actual — una
suscripción que falló por 429 esta vez conserva lo que ya tenía
persistido de una corrida anterior, en vez de perderlo.

### b) Job recurrente `/api/cron/historical-gap-backfill`
- Lógica extraída a `src/lib/historicalGapBackfill.ts`
  (`backfillTenantHistoricalGaps(tenantId, months=2)`), reusada por el
  cron y por el trigger on-demand (ver c).
- Recorre `Tenants WHERE status='active'` — automáticamente cubre
  tenants que se sumen al SaaS a futuro, sin tocar código.
- **Upsert-only** (`ON DUPLICATE KEY UPDATE`, nunca `DELETE`) —
  estructuralmente no puede repetir el incidente de arriba, a costo de no
  poder "limpiar" datos corruptos (para eso sigue existiendo el script
  manual con delete+insert, ahora con el guard mejorado).
- Programado **diario 03:00 UTC** (pedido explícito del usuario: todos
  los días, no semanal como propuse originalmente).

### c) Trigger on-demand al abrir el Invoicing Report
`triggerBackfillIfStale(tenantId)` en `historicalGapBackfill.ts`,
enganchado en `GET /api/admin/report/invoicing`:
- Fire-and-forget — no bloquea la respuesta de la página.
- Solo dispara si `CostSnapshots` no tiene filas de los últimos 2 días
  para ese tenant (`isTenantDataStale`).
- Debounced con un lock en Redis (`SET NX EX 21600`, 6h) — no le pega a
  Cost Management en cada carga de página.
