## 🟡 INC-01 — Falta de enforcement de rol RBAC en endpoints de escritura privilegiados

**Severidad:** MEDIUM · **Confianza:** 80% · **Categoría:** Broken Access Control (escalación de privilegios intra-tenant)

**Archivos:**
- `src/app/api/intelligence/unit-economics/route.ts:132` (POST — **nuevo en este ciclo**, commit `85c9dd8`)
- `src/app/api/budgets/alerts/route.ts:55` (POST crear alert rule — **reescrito este ciclo**, commit `d520937`)
- `src/app/api/budgets/route.ts:67` (POST crear/actualizar budget — preexistente)

**Problema:** estos endpoints de escritura autorizan con `requireTenantAccess(...)`, que solo verifica que el
caller **pertenezca al tenant**, sin chequear su rol. La app ya define y aplica un modelo más estricto para
escrituras privilegiadas en rutas hermanas:
- `src/app/api/budgets/create/route.ts:19` → `requireTenantRole(request, bodyTenantId, ['Admin','Owner'])`
- `src/app/api/budgets/alerts/[id]/route.ts:17` (DELETE) → `requireTenantRole(request, tenantId, ['Admin','Owner'])`

Resultado inconsistente: una alert rule solo puede **borrarse** por Admin/Owner, pero **crearse** por cualquier
miembro; un budget nativo Azure requiere Admin/Owner para crearse, pero la tabla `Budgets` puede escribirse por
cualquier miembro; y el nuevo config de DAU no tiene ningún gate de rol.

**Escenario de explotación:** un usuario con rol de bajo privilegio (p. ej. `Member`/`Viewer`) con token válido
de su propio tenant envía `POST /api/budgets/alerts?tenantId=<suTenant>`, `POST /api/intelligence/unit-economics`
o `POST /api/budgets`. La escritura tiene éxito pese a no ser Admin/Owner. Permite manipular límites/umbrales de
presupuesto, crear alert rules (eligiendo `channel`/`channelTarget`) y fijar el denominador DAU de unit-economics
— todos controles de gobernanza financiera pensados para Admin/Owner.

**Verificación:** comparación directa de código entre rutas hermanas del mismo feature. `requireTenantAccess`
(`requestAuth.ts:307`) retorna con solo membresía de tenant; `requireTenantRole` (`requestAuth.ts:345`) además
valida `Users.role` contra un allow-list.

**Remediación sugerida:** reemplazar `requireTenantAccess` por
`requireTenantRole(request, tenantId, ['Admin','Owner'])` en los tres handlers de escritura, alineándolos con
sus hermanas create/delete.

## 🟢 INC-02 — Validación de audience del JWT falla abierta si no hay env configurada

**Severidad:** LOW · **Confianza:** ~55% · **Categoría:** Security Misconfiguration
**Archivo:** `src/lib/requestAuth.ts:164-172` (preexistente, fuera del diff)

`validateAudience` retorna sin chequear cuando el allow-list de client-IDs está vacío (sin `AZURE_CLIENT_ID` /
`AZURE_AD_CLIENT_ID` / `NEXT_PUBLIC_*`). Si esas env vars quedan sin setear en algún ambiente, cualquier token
correctamente firmado por Entra para el propio tenant del caller —incluso emitido para otra audience/app— sería
aceptado. Impacto acotado (el caller sigue limitado a su propio `tid`), pero conviene **fail-closed** si no hay
audience configurada. Se documenta porque sustenta la superficie de INC-01.

## 🟢 INC-03 — MACC usa heurística de dominio en vez de super-admin verificado

**Severidad:** LOW · **Confianza:** ~55% · **Categoría:** RBAC / tier gating
**Archivo:** `src/app/api/intelligence/macc/route.ts:27,39`

`const isSuperAdmin = identity.isCorporateDomain;` saltea el gate de tier Enterprise usando solo la heurística de
dominio de email (`@cscloudsolutions.com.ar`), **sin** el chequeo de `system_role = 'SUPERADMIN'` en DB que sí
aplica `requireSuperAdmin` (`requestAuth.ts:293`). Difícil de explotar (el claim de email deriva de un token
firmado por Microsoft con UPN de dominio verificado), pero es un gate más débil que el patrón establecido.
**Remediación:** alinear con `requireSuperAdmin`/`hasSystemRole`.

## 🟢 INC-04 — Anomalies ejecuta el branch mock antes de autenticar

**Severidad:** LOW · **Confianza:** baja · **Categoría:** Consistencia / defensa en profundidad
**Archivo:** `src/app/api/intelligence/anomalies/route.ts:52-72`

El branch `isMockTenant` (y su `sendWebhookAlert`) se ejecuta **antes** de `requireTenantAccess` (línea 75), a
diferencia de las demás rutas que autentican primero. Solo afecta a los GUID de tenant demo fijos con data
estática, por lo que el impacto es negligible, pero la ordenación es inconsistente con el resto del código.
**Remediación:** mover el chequeo de auth antes del branch mock.

## ✅ Áreas verificadas sin hallazgos

- **Autenticación de requests:** JWT RS256 validado contra JWKS de Entra, issuer/audience/exp/nbf, tenant scoping. Correcto en todas las rutas revisadas.
- **SQL injection:** queries parametrizadas en todas las rutas (incl. `IN (...)` dinámico de anomalies con placeholders).
- **Aislamiento multi-tenant:** todas las queries filtran por `tenant_id`; `requireTenantAccess` valida pertenencia; cross-tenant solo con SUPERADMIN + dominio corp.
- **SSRF / webhooks:** allow-list + guard de IP privadas (`assertSafeWebhookUrl`).
- **Credenciales cloud:** `ClientSecretCredential` por tenant; `subscriptionId` del cliente no cruza tenants.
- **Migración `20260701-002-business-metrics.sql`:** idempotente (`CREATE TABLE IF NOT EXISTS`), tenant-scoped, tipos correctos (INT UNSIGNED, DATE, UNIQUE KEY por tenant+fecha).
