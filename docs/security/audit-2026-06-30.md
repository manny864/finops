## 🔴 CRITICAL

### C-01 — IDOR cross-tenant en Tag Compliance (sin autenticación)
**Archivo:** `src/app/api/tags/compliance/route.ts:26-31`
**Confianza:** Alta (verificado por lectura directa del código)

```ts
export async function GET(req: NextRequest) {
    const { searchParams } = new URL(req.url);
    const tenantId = searchParams.get('tenantId');
    // ❌ No requireTenantAccess / requireRequestIdentity / authGuard
    if (!tenantId) return NextResponse.json({ error: "Missing tenantId" }, { status: 400 });
    // ... usa getAzureCredential(tenantId) y consulta Azure Resource Graph
```

**Impacto:** Cualquier atacante con acceso HTTP puede pasar `?tenantId=<id-de-otro-cliente>` y obtener el inventario completo de recursos Azure, scoreo de cumplimiento de tags, y listado de Resource Groups del tenant víctima. Esto es información sensible (postura cloud, costos asociados, naming convention, blast radius).

**Remediación:** Insertar al inicio del handler:
```ts
await requireTenantRole(request, tenantId, ['Admin', 'Owner', 'Reader']);
```

**Nota:** Este endpoint fue agregado en commit `b3782e2` por mí (Copilot). Bug introducido por la asistente.

### C-02 — IDOR cross-tenant en 5 rutas /api/intelligence (sin autenticación)
**Confianza:** Alta

Estas rutas extraen `tenantId` de la request **sin validar identidad** y consultan Azure Cost Management / Resource Graph / Microsoft Graph con la credencial federada del tenant:

| Ruta | Línea | Fuente del tenantId |
|------|-------|---------------------|
| `src/app/api/intelligence/chargeback/route.ts` | L9 | `searchParams.get('tenantId')` |
| `src/app/api/intelligence/billing/route.ts` | L8 | header `x-tenant-id` |
| `src/app/api/intelligence/licenses/route.ts` | L9 | header `x-tenant-id` |
| `src/app/api/intelligence/rightsizing/route.ts` | L29 | header `x-tenant-id` |
| `src/app/api/intelligence/export/powerbi/route.ts` | L8 | `searchParams.get('tenantId')` |

**Impacto:** Igual que C-01, pero amplificado: chargeback expone datos por CostCenter (PII organizacional), licenses expone usuarios M365 inactivos (PII de empleados), rightsizing expone VMs con su utilización (información operacional sensible), export/powerbi puede leer credenciales si las llama (verificar).

**Patrón anti-pattern reutilizado** en varios endpoints: confiar en el header HTTP `x-tenant-id` sin JWT. Cualquier `curl -H "x-tenant-id: <victim-id>"` funciona.

**Remediación:** Para cada ruta, añadir:
```ts
await requireTenantRole(request, tenantId, ['Admin', 'Owner', 'Reader']);
```
Y **eliminar** el patrón `x-tenant-id` header — el tenantId debe leerse desde `identity.claims.tid` post-validación JWT, NO confiado del cliente.

### C-03 — TOTP brute-force en MFA verify-challenge
**Archivo:** `src/app/api/mfa/verify-challenge/route.ts`
**Confianza:** Alta

**Vulnerabilidad combinada:**
1. **No rate limit.** El endpoint llama `verifyToken(secret, token)` sin contar intentos.
2. **Challenge no se consume en fallo.** Línea 122: `UPDATE MfaChallenges SET consumed_at = NOW()` se ejecuta solo si `verified = true`. En fallo el mismo `challenge_id` queda válido para más intentos hasta que expire.

**Impacto:** Atacante con un JWT válido (ej. cuenta comprometida pre-MFA, o compromiso de un SSO downstream) puede:
- Pedir un challenge MFA.
- Forzar 1.000.000 de tokens TOTP de 6 dígitos antes de la expiración (típicamente 5 min).
- Espacio TOTP es 10⁶ → con conexión doméstica (~100 req/s) y ventana de 30s + window=1 (ver `mfa.ts:41`), se barre la mitad del espacio en <2 horas si la ventana de challenge es larga.

**Remediación combinada:**
1. Consumir el challenge en CADA intento (success o fail) o incrementar `attempt_count`, max 5.
2. Aplicar `rateLimiter` por `challenge_id` y por `email`: max 5 intentos por minuto, lockout exponencial.
3. Reducir `expires_at` del challenge a 60-120s.

### C-04 — Ausencia total de Security Headers (CSP/HSTS/X-Frame/etc.)
**Archivo:** `next.config.ts` (11 líneas, sin bloque `headers()`)
**Confianza:** Alta

```ts
const nextConfig: NextConfig = {
  output: 'standalone',
  distDir: process.env.PORT ? `.next-${process.env.PORT}` : '.next',
  serverExternalPackages: ['mysql2'],
};
```

**Faltan:**
- `Content-Security-Policy` → no hay defensa en profundidad contra XSS si aparece uno.
- `Strict-Transport-Security` (HSTS) → downgrade attack vía MITM en primera conexión (aunque CloudFlare provee HSTS si está configurado, no es de la app).
- `X-Frame-Options: DENY` o `frame-ancestors 'none'` → clickjacking sobre el dashboard, capture de tokens MFA.
- `X-Content-Type-Options: nosniff` → MIME confusion attacks.
- `Referrer-Policy: strict-origin-when-cross-origin` → leakage de URLs sensibles (con tenantId en query).
- `Permissions-Policy` → exposición de APIs del browser.

**Impacto:** Multiplica severidad de cualquier XSS/clickjacking que aparezca, y permite enmarcar la app para phishing de credenciales.

**Remediación:** Agregar `async headers()` en `next.config.ts` con la baseline OWASP. Si CloudFlare ya pone HSTS, mantenerla en app también (defense in depth).

### C-05 — Denial of Wallet via /intelligence/upload
**Archivo:** `src/app/api/intelligence/upload/route.ts`
**Confianza:** Alta

Endpoint POST público (**sin auth, sin rate limit, sin CAPTCHA**) que:
1. Recibe JSON arbitrario en `body.data`.
2. Llama `normalizeBillingCsv()` (procesamiento CPU sobre arrays arbitrariamente grandes).
3. Llama `getAssessment(summaryData)` → **invoca Gemini AI con tu API key**.

**Impacto:**
- Atacante itera `for i in {1..10000}; do curl -X POST https://finops.cscloudsolutions.com.ar/api/intelligence/upload -d '{"data":[...]}'`
- Cada request consume tokens de Gemini ($$$).
- CPU del VPS al máximo procesando arrays.
- Sin auth no hay forma de attribuir/blackhole al atacante.

**Remediación:** Auth obligatoria (JWT o API key) + rate limit por IP (5/min) + límite estricto en `body.data.length` (ej. 10.000 filas máximo).

### M-02 — Marketplace activate endpoints sin signature de Microsoft
**Archivos:**
- `src/app/api/webhooks/marketplace/azure/activate/route.ts`
- `src/app/api/webhooks/marketplace/aws/activate/route.ts`

**Confianza:** Media

Los endpoints reciben un `token` opaco del cliente y lo resuelven contra Microsoft SaaS Fulfillment / AWS Marketplace. La validación efectiva es delegada al provider. Esto es por diseño (el token solo es resolvable por el provider), pero:
- Si Microsoft devuelve OK, se **crea Tenant + activa subscripción** automáticamente. Un token replay attack (mismo token usado 2 veces) podría crear tenants duplicados.
- No hay idempotency key.

**Remediación:** Almacenar `subscription_id` con UNIQUE constraint y `ON DUPLICATE KEY UPDATE`. Validar `activation_status` antes de crear.

### M-03 — JWT bypass via X-Cron-Auth — superficie agregada (auto-review)
**Archivo:** `src/lib/requestAuth.ts:267-301` (commit `a8af9a2`, agregado por mí)
**Confianza:** Alta

El bypass está bien implementado (timing-safe, length check, fail-closed, scope = tenantId), PERO:
- **Concede acceso a CUALQUIER `tenantId`** mientras tenga el secret. Si CRON_SECRET se filtra (logs, env dump, backup), un atacante puede leer todos los tenants.
- No hay logging de uso del bypass para auditoría.

**Remediación:**
1. Loggear cada uso del bypass: `console.warn('[CRON-AUTH] used for tenant=', tenantId, 'origin=', request.headers.get('x-forwarded-for'))`.
2. Validar que la request venga del propio servidor (X-Forwarded-For = 127.0.0.1 o IP del VPS).
3. Considerar rotar `CRON_SECRET` cada 30 días.

### M-04 — JWT `email` claim resolution acepta múltiples sources (privilege smuggling)
**Archivo:** `src/lib/requestAuth.ts:174-184`
**Confianza:** Media

```ts
const candidates = [claims.preferred_username, claims.unique_name, claims.upn, claims.email];
const found = candidates.find(...);
return found.toLowerCase();
```

Microsoft Entra emite estos claims con semánticas distintas (preferred_username puede ser email-no-verificado del externo, upn es la identidad oficial). Tomar el "primero que aparezca" puede permitir privilege escalation si un usuario externo controla `preferred_username` y el sistema mapea ese email a roles en DB.

**Remediación:** Usar **solo** `upn` (canónico) o `oid` (no-spoofable). Si necesitas display name, usar `preferred_username` por separado pero NUNCA para autorización.

### L-03 — Build artifact en distDir variable
**Archivo:** `next.config.ts:7`


## ✅ Áreas auditadas y limpias

### A-01 — JWT signature verification
`src/lib/requestAuth.ts:186-228` — Implementación correcta:
- Algoritmo restringido a `RS256` (rechaza `alg:none` y simétricos).
- JWKS fetch por tenant.
- `crypto.verify('RSA-SHA256', ...)` con clave pública JWK.
- Validación de `aud`, `iss`, `exp`, `nbf`, `tid` con clock skew.
- Issuer allowlist.

### A-02 — SQL queries parametrizadas
175 rutas API + módulos de storage. Todas las queries de pool/connection usan placeholders `?`. Únicas excepciones: `ALTER TABLE ${col}` en `db.ts` y `intelligence/storage-efficiency/route.ts` — donde `col` proviene de array hardcodeado, NO de input. **No hay SQL injection.**

### A-03 — Paddle webhook signature verification
`src/app/api/webhooks/paddle/route.ts:13-60` — Correcto:
- HMAC SHA256 con secret server-only.
- Replay window de 5 min.
- `crypto.timingSafeEqual` con length check previo.
- Verificación antes de procesar el payload.

### A-04 — MFA cryptography
`src/lib/mfaCrypto.ts` — Correcto:
- AES-256-GCM (AEAD, autenticado).
- IV aleatorio por mensaje (no estático).
- Key de 256 bits desde `MFA_ENCRYPTION_KEY` (64 hex chars).
- Fail-closed si la key falta o tiene longitud incorrecta.
- Recovery codes hasheados (no plaintext).
