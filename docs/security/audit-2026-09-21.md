## SEC-01 — El motor de prueba de alertas era un relay saliente (MEDIUM-HIGH)

**Ubicación:** `src/services/azureSelfServiceAlerts.service.ts:398` (`testAlertRuleDelivery`) y
`src/app/api/analytics/self-service-alerts/test/route.ts`.
**Estado antes del fix:** desplegado en producción.

### El defecto

La URL de destino **venía en el body del request**, no de la regla guardada en la base:

```ts
const targetUrl = rule.channelConfig.webhookUrl || rule.channelConfig.channelTarget;

if (targetUrl && (targetUrl.startsWith("http://") || targetUrl.startsWith("https://"))) {
  const response = await fetch(targetUrl, { method: "POST", ... });
```

El `rule` se deserializa directo de `await request.json()`. La única validación era el prefijo del
esquema — que **acepta `http://` plano**. No había allow-list de hosts, ni rechazo de rangos privados,
ni bloqueo de redirects.

Y el resultado volvía al llamador con el status:

```ts
return { success: response.ok, httpStatusCode: response.status, ... }
```

### Por qué importa: el hermano ya lo hacía bien

`src/app/api/admin/config/integrations/test-webhook/route.ts` hace exactamente lo mismo —probar un
webhook— y está correctamente endurecido. Su comentario de cabecera describe el riesgo con precisión:

> RBAC: `requireTenantRole(['Admin','Owner'])`. Es un POST saliente desde nuestra infraestructura hacia
> una URL que elige el usuario — `requireTenantAccess` (cualquier miembro del tenant) convertiría el
> endpoint en un relay de requests.

La ruta de self-service alerts hacía **las dos cosas** que ese comentario desaconseja: `requireTenantAccess`
y URL sin validar. La defensa existía en el repo (`src/lib/webhookSecurity.ts`, usada por
`notifications.ts` en sus tres puntos de envío real); este camino se quedó atrás.

### Escenario de explotación

Un usuario con el rol **más bajo** de cualquier tenant (un Reader, que no puede ni crear una regla de
alerta) hace:

```
POST /api/analytics/self-service-alerts/test?tenantId=<su-tenant>
{ "notificationChannel": "WEBHOOK", "channelConfig": { "webhookUrl": "http://10.0.0.5:8080/" } }
```

y obtiene el status HTTP de vuelta. Con eso barre hosts y puertos internos de la red de Container Apps
usando el status y el timing como oráculo, y usa nuestra IP de salida como origen de POSTs arbitrarios
contra terceros.

**Lo que NO permite**, y por eso no es HIGH: sólo vuelven `status` y `statusText`, no el cuerpo de la
respuesta, así que no hay exfiltración directa de contenido. IMDS de Azure (`169.254.169.254`) exige el
header `Metadata: true`, que este código no manda, así que las credenciales de la managed identity no
estaban alcanzables por esta vía.

### Remediación aplicada

1. `assertSafeWebhookUrl(targetUrl)` **antes** del `fetch`, que impone HTTPS, allow-list de hosts
   (Slack/Teams/Logic Apps/PagerDuty…), rechazo de IP literales y resolución DNS con rechazo de rangos
   privados y link-local.
2. `redirect: "error"` en el `fetch`: un 302 sacaría el POST de la allow-list.
3. La ruta pasó a `requireTenantRole(['Admin','Owner'])`, que es lo que ya exigían el POST, el PUT y el
   DELETE de la ruta hermana. **No rompe UX legítima:** sin esos roles no se puede crear la regla que se
   iba a probar. Era la única operación mutante del módulo abierta a cualquier miembro.

Fijado en `__tests__/unit/ssrfPruebaDeAlerta.test.ts` (4 aserciones sobre el fuente: guard presente,
guard **antes** del fetch, redirects bloqueados, RBAC correcto).

## SEC-02 — `?mock=true` desactiva el guard en 37 rutas, y la autorización queda delegada al servicio (MEDIUM, ABIERTO)

**No explotable hoy. Se verificó una por una.** Se reporta porque el modo de falla es silencioso y está a
un descuido de ser crítico.

### El patrón

**86 rutas** leen `searchParams.get("mock") === "true"`. En **49** eso corta con un `return` de datos
fabricados y no hay más nada que discutir. En las otras **37** el parámetro desactiva el guard y la
ejecución **sigue**, pasando el flag a la capa de servicio:

```ts
const isMock = searchParams.get("mock") === "true";
if (!isMock) {
    await requireSuperAdmin(request);
}
const tenants = await listAllTenantsForSuperAdmin(isMock);   // ← la autorización real vive acá
```

**26 de esas 37 son `superadmin/*`**: el listado de todos los tenants, la config global de IA, el embudo
de inscripción con datos de leads, el alta manual de tenants, los links de checkout de Paddle.

Nótese que el flag es un **query param que manda el llamador**, no `isMockTenant(tenantId)`. No hace
falta adivinar ningún identificador: basta con agregar `?mock=true` a la URL.

### Por qué hoy no se puede explotar

Se rastrearon las **22 funciones de servicio** que reciben `isMock` desde una ruta con este gate y se
leyó cada una. **Las 22 cortan antes de tocar la base**, en una de dos formas:

```ts
if (isMock) { return [...MOCK_SUPERADMIN_TENANTS]; }   // corte positivo (15)
if (!isMock) { await pool.query(`INSERT ...`); }        // guarda negativa  (7)
```

`createManualTenant` merece la mención aparte: su corte positivo está **después** de ~30 líneas que
arman el objeto de respuesta, así que un barrido que sólo mire la cabecera de la función lo marca como
faltante. Corta bien, pero es el que más se parece al descuido que este finding describe.

O sea que hoy un `?mock=true` anónimo devuelve datos inventados y no escribe nada. Lo verifiqué en las
que más duelen: `listAllTenantsForSuperAdmin`, `getPlatformGlobalAiSettings`, `getSignupFunnelAnalytics`,
`createManualTenant`, `triggerCronJob`, `reseedPricingUnitsCatalog`, `configurePartnerMpn`,
`relinkPartner`, `generatePaddleCheckoutLink` y los dos de `loadTesting.service`.

### Por qué igual es un finding

1. **La autorización de 26 rutas SuperAdmin depende de que cada función de servicio se acuerde de cortar.**
   No hay nada que lo obligue. La primera que no lo haga es disclosure no autenticado del dato que sirva.
2. **El guard mecánico existente da falsa tranquilidad para esta clase.**
   `__tests__/unit/guardRutasApi.test.ts` pasa en verde: sólo afirma que la ruta *invoca* un mecanismo de
   auth, y estas lo invocan — dentro de un `if`. Es la contracara de lo que la auditoría anterior ya
   había advertido sobre ese test ("lo que NO afirma es que el guard sea el correcto, y que corra antes
   del efecto").
3. **Es frágil por construcción.** Un `createManualTenant` nuevo, escrito por alguien que copia la firma
   `(payload, isMock = false)` y se olvida del corte, crea tenants sin autenticación.

### Recomendación

Dos caminos, en orden de preferencia:

- **Sacar el gate del query param.** La demo no necesita pegarle a rutas de SuperAdmin sin sesión: puede
  resolverse con un tenant de demo real y sesión de demo. Es el arreglo que elimina la clase entera.
- **Si el gate se queda**, atarlo con un test del mismo estilo que los que ya usa la casa: para cada
  función que recibe `isMock` desde una ruta con gate, afirmar que el fuente corta (`if (isMock) return`
  o `if (!isMock) { … }`) antes de cualquier `pool.query`. Es mecánico y corre en milisegundos.

No lo aplico por mi cuenta: la primera opción toca el flujo de demo, que es una decisión de producto.

## OBS-01 — Chequeos que corren antes del guard

Tres rutas resuelven algo del input **antes** de autenticar:

tempranas alguna vez consulta la base o Azure, pasa a ser un finding real.

  markup. Se verificó la puerta de entrada —la firma del webhook de Paddle, que está bien— pero **no** la

  la prioridad del próximo ciclo.

  remediaciones, las colas de prioridad. Se auditó que autentiquen, no su lógica interna.

  código, no se leyó una por una.
