## SEC-01 — El motor de prueba de alertas era un relay saliente (MEDIUM-HIGH)

**Ubicación:** `src/services/azureSelfServiceAlerts.service.ts:398` (`testAlertRuleDelivery`) y
`src/app/api/analytics/self-service-alerts/test/route.ts`.
**Estado antes del fix:** desplegado en producción.

### El defecto

La URL de destino **venía en el body del request**, no de la regla guardada en la base:

```ts
const targetUrl = rule.channelConfig.webhookUrl || rule.channelConfig.channelTarget;

if (targetUrl && (targetUrl.startsWith("http://") || targetUrl.startsWith("https://"))) {
  const response = await fetch(targetUrl, { method: "POST", ... });
```

El `rule` se deserializa directo de `await request.json()`. La única validación era el prefijo del
esquema — que **acepta `http://` plano**. No había allow-list de hosts, ni rechazo de rangos privados,
ni bloqueo de redirects.

Y el resultado volvía al llamador con el status:

```ts
return { success: response.ok, httpStatusCode: response.status, ... }
```

### Por qué importa: el hermano ya lo hacía bien

`src/app/api/admin/config/integrations/test-webhook/route.ts` hace exactamente lo mismo —probar un
webhook— y está correctamente endurecido. Su comentario de cabecera describe el riesgo con precisión:

> RBAC: `requireTenantRole(['Admin','Owner'])`. Es un POST saliente desde nuestra infraestructura hacia
> una URL que elige el usuario — `requireTenantAccess` (cualquier miembro del tenant) convertiría el
> endpoint en un relay de requests.

La ruta de self-service alerts hacía **las dos cosas** que ese comentario desaconseja: `requireTenantAccess`
y URL sin validar. La defensa existía en el repo (`src/lib/webhookSecurity.ts`, usada por
`notifications.ts` en sus tres puntos de envío real); este camino se quedó atrás.

### Escenario de explotación

Un usuario con el rol **más bajo** de cualquier tenant (un Reader, que no puede ni crear una regla de
alerta) hace:

```
POST /api/analytics/self-service-alerts/test?tenantId=<su-tenant>
{ "notificationChannel": "WEBHOOK", "channelConfig": { "webhookUrl": "http://10.0.0.5:8080/" } }
```

y obtiene el status HTTP de vuelta. Con eso barre hosts y puertos internos de la red de Container Apps
usando el status y el timing como oráculo, y usa nuestra IP de salida como origen de POSTs arbitrarios
contra terceros.

**Lo que NO permite**, y por eso no es HIGH: sólo vuelven `status` y `statusText`, no el cuerpo de la
respuesta, así que no hay exfiltración directa de contenido. IMDS de Azure (`169.254.169.254`) exige el
header `Metadata: true`, que este código no manda, así que las credenciales de la managed identity no
estaban alcanzables por esta vía.

### Remediación aplicada

1. `assertSafeWebhookUrl(targetUrl)` **antes** del `fetch`, que impone HTTPS, allow-list de hosts
   (Slack/Teams/Logic Apps/PagerDuty…), rechazo de IP literales y resolución DNS con rechazo de rangos
   privados y link-local.
2. `redirect: "error"` en el `fetch`: un 302 sacaría el POST de la allow-list.
3. La ruta pasó a `requireTenantRole(['Admin','Owner'])`, que es lo que ya exigían el POST, el PUT y el
   DELETE de la ruta hermana. **No rompe UX legítima:** sin esos roles no se puede crear la regla que se
   iba a probar. Era la única operación mutante del módulo abierta a cualquier miembro.

Fijado en `__tests__/unit/ssrfPruebaDeAlerta.test.ts` (4 aserciones sobre el fuente: guard presente,
guard **antes** del fetch, redirects bloqueados, RBAC correcto).

## SEC-02 — `?mock=true` desactiva el guard en 37 rutas, y la autorización queda delegada al servicio (MEDIUM, ABIERTO)

**No explotable hoy. Se verificó una por una.** Se reporta porque el modo de falla es silencioso y está a
un descuido de ser crítico.

### El patrón

**86 rutas** leen `searchParams.get("mock") === "true"`. En **49** eso corta con un `return` de datos
fabricados y no hay más nada que discutir. En las otras **37** el parámetro desactiva el guard y la
ejecución **sigue**, pasando el flag a la capa de servicio:

```ts
const isMock = searchParams.get("mock") === "true";
if (!isMock) {
    await requireSuperAdmin(request);
}
const tenants = await listAllTenantsForSuperAdmin(isMock);   // ← la autorización real vive acá
```

**26 de esas 37 son `superadmin/*`**: el listado de todos los tenants, la config global de IA, el embudo
de inscripción con datos de leads, el alta manual de tenants, los links de checkout de Paddle.

Nótese que el flag es un **query param que manda el llamador**, no `isMockTenant(tenantId)`. No hace
falta adivinar ningún identificador: basta con agregar `?mock=true` a la URL.

### Por qué hoy no se puede explotar

Se rastrearon las **22 funciones de servicio** que reciben `isMock` desde una ruta con este gate y se
leyó cada una. **Las 22 cortan antes de tocar la base**, en una de dos formas:

```ts
if (isMock) { return [...MOCK_SUPERADMIN_TENANTS]; }   // corte positivo (15)
if (!isMock) { await pool.query(`INSERT ...`); }        // guarda negativa  (7)
```

`createManualTenant` merece la mención aparte: su corte positivo está **después** de ~30 líneas que
arman el objeto de respuesta, así que un barrido que sólo mire la cabecera de la función lo marca como
faltante. Corta bien, pero es el que más se parece al descuido que este finding describe.

O sea que hoy un `?mock=true` anónimo devuelve datos inventados y no escribe nada. Lo verifiqué en las
que más duelen: `listAllTenantsForSuperAdmin`, `getPlatformGlobalAiSettings`, `getSignupFunnelAnalytics`,
`createManualTenant`, `triggerCronJob`, `reseedPricingUnitsCatalog`, `configurePartnerMpn`,
`relinkPartner`, `generatePaddleCheckoutLink` y los dos de `loadTesting.service`.

**Confirmado contra producción, no sólo por lectura de código.** Un GET anónimo a
`/api/superadmin/tenants?mock=true` sobre `finops.cscloudsolutions.com.ar` responde 200 con
`tenant-acme-prod` / `ACME Corporation` / `entraTenantId: 01234567-89ab-cdef-0123-456789abcdef`, que es
byte por byte `MOCK_SUPERADMIN_TENANTS` (`superAdminTenants.service.ts:125`). Ningún cliente real sale
por ahí. El GUID secuencial es el discriminador rápido para repetir esta prueba en el futuro.

Detalle menor que vale anotar: ese registro mock lleva `salesRepName: "Juan Manuel Chavez"`, un nombre
real servido a un llamador anónimo. Es el dueño de la empresa y el dato es público, así que no se cuenta
como finding, pero un `"Vendedor Demo"` no costaría nada.

### Por qué igual es un finding

1. **La autorización de 26 rutas SuperAdmin depende de que cada función de servicio se acuerde de cortar.**
   No hay nada que lo obligue. La primera que no lo haga es disclosure no autenticado del dato que sirva.
2. **El guard mecánico existente da falsa tranquilidad para esta clase.**
   `__tests__/unit/guardRutasApi.test.ts` pasa en verde: sólo afirma que la ruta *invoca* un mecanismo de
   auth, y estas lo invocan — dentro de un `if`. Es la contracara de lo que la auditoría anterior ya
   había advertido sobre ese test ("lo que NO afirma es que el guard sea el correcto, y que corra antes
   del efecto").
3. **Es frágil por construcción.** Un `createManualTenant` nuevo, escrito por alguien que copia la firma
   `(payload, isMock = false)` y se olvida del corte, crea tenants sin autenticación.

### Recomendación

Dos caminos, en orden de preferencia:

- **Sacar el gate del query param.** La demo no necesita pegarle a rutas de SuperAdmin sin sesión: puede
  resolverse con un tenant de demo real y sesión de demo. Es el arreglo que elimina la clase entera.
- **Si el gate se queda**, atarlo con un test del mismo estilo que los que ya usa la casa: para cada
  función que recibe `isMock` desde una ruta con gate, afirmar que el fuente corta (`if (isMock) return`
  o `if (!isMock) { … }`) antes de cualquier `pool.query`. Es mecánico y corre en milisegundos.

### Lo que se hizo (2026-09-21)

Se eligió la segunda: **`__tests__/unit/corteMockAntesDeIO.test.ts`**. El gate del query param **sigue en
pie**, así que la clase no está eliminada — está atada.

El test no lleva lista escrita a mano: descubre las rutas con gate recorriendo `src/app/api`, extrae de
ellas los nombres invocados pasando `isMock`, los resuelve contra `src/services` y `src/lib`, y por cada
uno compara la posición del primer `if (isMock)` / `if (!isMock)` contra la del primer `pool.query`,
`await fetch(` o `redis.*`. Una ruta nueva con el gate, o una función nueva que reciba el flag, entran
solas sin que nadie se acuerde de registrarlas.

**Validado con mutantes, no sólo por pasar en verde.** Se rompió `listAllTenantsForSuperAdmin` de las dos
formas posibles y el test las distingue:

| Mutante | Mensaje |
|---|---|
| Corte eliminado | `hace E/S pero NUNCA mira isMock. Un ?mock=true anonimo llega hasta la base.` |
| Corte movido después del `pool.query` | `mira isMock DESPUES de su primera E/S. El corte tiene que ir antes.` |

Lleva además una aserción de piso (`>20` rutas, `>10` funciones) para que un refactor que renombre
`isMock` dé rojo en vez de pasar en verde por no encontrar nada — verde por vacío es peor que rojo.

**Lo que el test NO cubre**, y sigue siendo revisión humana: la E/S **indirecta**. Una función que no
llame a `pool.query` sino a un helper que consulte adentro se ve limpia. Por eso SEC-02 queda MITIGADO y
no CERRADO: el arreglo que elimina la clase entera sigue siendo sacar el gate del query param.

### CORRECCIÓN (2026-09-22): ese arreglo de fondo no está disponible

Al mirar el flujo de demo para tomar la decisión, resultó que **sacar el gate rompe la demo pública
entera**. La recomendación de arriba no se sostiene y queda anotada como lo que era: una conclusión sacada
sin haber leído el flujo de demo.

`/[locale]/demo` entra con usuario `demo` / contraseña `demo`, y `setDemoSession` deja una cookie
`finops_demo_session` con `{isDemo:true, tier, provider}`. **Eso no es una identidad de Entra.**
`requireSuperAdmin` y `requireTenantAccess` van los dos a `requireRequestIdentity`, que valida un token
MSAL: la sesión de demo no pasa ninguno. El visitante de la demo está, desde la óptica de la API, sin
autenticar — y el gate `?mock=true` es exactamente lo que hace que vea algo.

Mover el gate del query param a la cookie tampoco alcanza: esa cookie es JSON **sin firmar**, igual que la
de impersonación que marcó la auditoría del 09-07, así que falsificarla cuesta lo mismo que agregar el
parámetro.

**Qué cambia en el finding.** El riesgo de SEC-02 nunca fue "se sirven datos mock sin token" — eso es el
producto: la demo es pública a propósito y es, hoy, la principal herramienta de venta. El riesgo es el
otro: **que una función de servicio se olvide de honrar `isMock` y le sirva datos REALES a un llamador
anónimo.** Contra eso, `corteMockAntesDeIO.test.ts` no es un parche provisorio a la espera del arreglo
bueno: **es el arreglo**, dentro de lo que permite el diseño del producto.

Sigue MITIGADO y no CERRADO por el motivo de siempre —no ve la E/S indirecta a través de un helper—.
Cerrarlo del todo pide que la demo deje de ser anónima: un tenant de demo real, con datos sembrados y
sesión de verdad. Eso es un cambio de producto, no de seguridad, y con la demo funcionando de herramienta
de venta no es el momento.

## FIN-01 — Un reembolso revertía al afiliado y le pagaba igual al comercial (HIGH)

**Ubicación:** `src/services/affiliates.service.ts:192` (`revertirComision`), llamada desde
`handleTransactionRefunded` en el webhook de Paddle.
**Estado antes del fix:** desplegado en producción.

### El defecto

`Commissions` es el libro **unificado**: la migración `20260913-006` lo dice en su encabezado y el motor
del comercial escribe ahí desde entonces, al lado del de afiliados. Pero la reversión seguía acotada al
tipo que existía cuando se escribió:

```sql
UPDATE Commissions SET status = 'REVERSED'
 WHERE beneficiary_type = 'affiliate' AND paddle_transaction_id = ?
   AND status IN ('PENDING', 'DUE', 'APPROVED')
```

`revertirComision` es el **único** lugar del código que pone `REVERSED`. O sea que la cuota del comercial
no tenía ninguna vía de reversión: ni por reembolso, ni por nada.

### Qué pasaba con plata real

Cliente paga, la casa devenga dos comisiones sobre ese cobro —la del afiliado que lo trajo y la cuota del
comercial que lo cerró, que el propio código documenta como dos filas legítimas del mismo cobro—. El
cliente pide reembolso. Paddle manda `transaction.refunded`. Se revierte la del afiliado y **la del
comercial queda en `PENDING`/`DUE`, entra al panel de liquidación y se paga.** La casa devolvió la venta y
pagó igual el 20% sobre ella.

Nada lo detecta: la comisión del comercial es una fila válida, con su transacción, su monto y su
vencimiento. Sólo aparecería conciliando el libro de comisiones contra los reembolsos, que no se hace.

En un contrato **anual** duele más: es una sola cuota que vale el 20% del año entero.

### Por qué se coló

No fue un error de criterio, fue un desfase de seis días. El 2026-09-07 el filtro era correcto: sólo
existían comisiones de afiliado. El 2026-09-13 el motor del comercial empezó a escribir en la misma tabla
y nadie volvió sobre la reversión. Es el modo de falla clásico de unificar un almacén sin revisar a todos
los que ya lo leían.

### Remediación aplicada

Se sacó el filtro por `beneficiary_type`: la reversión ahora alcanza a todo el libro para esa transacción.
`PAID` sigue afuera a propósito — descontarle a alguien algo que ya cobró es una decisión contable, no el
efecto de un webhook.

## FIN-02 — El tenant que se daba de baja y volvía dejaba de devengar para siempre (MEDIUM)

**Ubicación:** `src/services/commissions.service.ts:144` (`devengarComisionComercial`).
**Estado antes del fix:** desplegado en producción.

### El defecto

La cuota se numeraba contando las filas vivas:

```sql
SELECT COUNT(*) AS n FROM Commissions
 WHERE beneficiary_type = 'sales_rep' AND tenant_id = ? AND status <> 'CANCELLED'
```

Pero `cancelarComisionesPorChurn` **sólo cambia el estado** — la fila conserva su `installment_number`, y
con él su lugar en el índice `uq_commission_installment (beneficiary_type, beneficiary_id, tenant_id,
installment_number)`.

Las dos cosas juntas se muerden: el conteo baja, el índice no.

### La secuencia

| Paso | Estado | Conteo | Próxima cuota | Resultado |
|---|---|---|---|---|
| Cuotas 1-3 devengadas | 1 `DUE`, 2 `DUE`, 3 `PENDING` | 3 | 4 | ok |
| El tenant se da de baja | la 3 pasa a `CANCELLED` | 2 | — | ok, es la regla de MEJ-14 |
| Vuelve y paga | — | 2 | **3** | choca con la cancelada |

El `INSERT IGNORE` descarta la fila, `affectedRows` da 0 y la función informa `"ya-devengada"` — que se lee
como la idempotencia haciendo su trabajo. **Y no se destraba nunca:** el cobro siguiente vuelve a contar 2,
vuelve a intentar la 3 y vuelve a chocar. El comercial deja de cobrar por ese tenant de forma permanente,
sin un error en ningún lado.

Es el espejo de FIN-01: aquel pagaba de más, éste paga de menos. Los dos en silencio.

### Remediación aplicada

La numeración pasa a `COALESCE(MAX(installment_number), 0)`, sin excluir canceladas. **Una cuota cancelada
o revertida es un lugar gastado, no uno libre.** El que vuelve sigue en la 4, no reintenta la 3. El tope de
12 y la regla del contrato anual no cambian, y para una secuencia sin bajas `MAX` y `COUNT` dan lo mismo,
así que el camino normal queda idéntico.

Fijado en `__tests__/unit/comisionesReembolsoYRealta.test.ts`, que cubre los dos findings.

## OBS-02 — El DDL promete una protección que el índice no da

`migrations/20260913-006` dice, sobre `uq_commission_installment`:

> Un comercial no devenga dos veces la misma cuota, aunque Paddle mande dos cobros el mismo mes (reintento
> de pago fallido, prorrateo de un cambio de plan).

**La segunda mitad no se cumple.** `installment_number` es un contador de cuotas devengadas, no un índice
del mes: dos cobros en el mismo mes producen la cuota N y la N+1, que son valores distintos y entran las
dos sin tocar el índice. Lo que el índice sí protege —y es valioso— es la carrera entre dos entregas
concurrentes que calculan el mismo número.

**Impacto real: chico.** Un cambio de plan a mitad de contrato consume una cuota antes de tiempo, así que
las 12 se completan en menos de 12 meses. El total sigue acotado por el tope de 12. No se remedia; se
anota porque el comentario invita a confiar en una garantía que no existe, y la próxima persona que
razone sobre prorrateos va a partir de una premisa falsa.


## Auditado y limpio

Vale registrar los resultados negativos, que son la mitad del trabajo:

- **Aislamiento de tenant en claves de caché** (frente heredado #2). Limpio. Todas las claves incluyen
  `tenantId`; la única global es `latest|${target}` en `src/lib/fx.ts`, que son cotizaciones de moneda y
  corresponde que sea compartida. El `cost:mtdsplit:v1` sin tenant que aparece en `dashboard/summary` es
  un comentario histórico de un cache que se eliminó: la clave viva es
  `cost:mtd:v1:${tenantId}:${subscriptionId}:${ym}`.
- **SSRF en `test-webhook` y `test-itsm`** (frente heredado #3). Los dos correctamente endurecidos:
  `requireTenantRole(['Admin','Owner'])`, validación de URL, `redirect: 'error'`, timeout. `test-itsm`
  además prueba las credenciales **guardadas** y no las del body.
- **Webhook de Paddle.** Correcto de manual: ventana de replay, y comparación de HMAC con
  `crypto.timingSafeEqual` precedida del chequeo de longitud.
- **Las 14 rutas nuevas del ciclo.** Todas con guard, salvo cuatro: dos crons que validan
  `CRON_SECRET` con bearer, `pricing/modules` (pública a propósito, como `pricing/plans`) y
  `commitments/breakeven`, que está en la lista de públicas del guard test con motivo escrito y es una
  función matemática pura, sin base ni datos de tenant. Verificado, no asumido.
- **`/api/remediation`.** El orden es correcto: rol → tier → bloqueo por delegación → borrado.
- **Doble acreditación por reintento de webhook: bien resuelta**, y en tres capas. `BillingTransactions`
  tiene UNIQUE en `paddle_transaction_id` y el handler trata `ER_DUP_ENTRY` como éxito en vez de
  propagarlo — importa, porque un 500 ahí dejaría a Paddle reintentando en loop y, peor, cortaría el flujo
  antes de los devengos. `Commissions` suma dos UNIQUE: uno por `(beneficiary_type, paddle_transaction_id)`
  y otro por cuota, que además cierra la carrera entre dos entregas concurrentes. Los devengos usan
  `INSERT IGNORE` y miran `affectedRows`.
- **La aritmética de la comisión.** `Decimal` de punta a punta con `ROUND_HALF_UP` a 4 decimales, y una
  `sumarMeses` que no desborda el día (31 de enero + 1 mes = 28/29 de febrero, no el 2 de marzo — con
  `setMonth` un vencimiento se adelantaría de mes).
- **Markup.** `Decimal` en todo el cálculo, una sola aplicación por línea, precedencia de overrides
  (suscripción → categoría de servicio → global) sin solaparse. Y los totales se acumulan desde las líneas
  **ya redondeadas**, que es lo correcto para una factura: las líneas suman exacto el total que se muestra.
- **Recálculo al cambiar de tier.** No hay recálculo retroactivo, y está bien: la base de cada cuota es el
  cobro que la originó, así que un cambio de plan entra solo en la cuota siguiente.
